## 引言

本文会介绍大规模中文网络图片数据集 [OmniCorpus-CW](https://openxlab.org.cn/datasets/Li-Qingyun/OmniCorpus-CW) [^li_omnicorpus] 中原图的数据爬取经验。这个数据集提供图文交错的语料，每篇网页存成一段段文字和其中图片的链接，大多是微信，小红书，知乎上的内容。

我们使用了 Hetzner 的95 台云服务器，爬取费用花费 175 美元，在 79 小时 25 分钟里保存了 2,973,430,108 张（99.62%），共 744 TB，平均每秒约 1 万张、2.6 GB/s。对于一个从来没有做过大规模爬虫的我来说，这个时间和速度已经非常令人满意。

另外值得注意的是，这三天里，几乎所有运维都是 AI agent 做的：巡检、调速、开删机器、排查事故和算账。我只做要花钱、加资源和有风险的决定。本文先讲这套分工怎么搭、agent 实际做了什么、它犯过哪些错，再讲爬虫怎么写、怎么提速和省钱，最后记一下从国内用 Hetzner 要过的几道手续。

## 让 AI agent 来运维

我这次使用了 Claude Code（CC） 来管理和运维整个爬虫系统，模型 Opus 5.5. 当然我认为未来我们不需要智能程度这么高的模型参与，比如我觉得当下的 deepseek 4 模型就足够了。只是说需要人再多操心些而已。

Hetzner 平台提供 api token，可以非常方便让模型自己去掌控服务器的开关机，所以在一开始我就把这些权限授权给了 Claude Code，而且我授权他可以自己的进行爬虫速率探测和调节，但是不允许因为反爬虫机制（比如限流、挑战页）而随意删机或改变策略。

白天CC每小时巡检一次，夜里每 30 分钟一次；另外还有事件监控，出了问题会马上叫醒它。三天下来，工作日志写了 2,600 多行。下面是几个例子：

- **微信调速：** 加机器后，所有机器同时、同比例地掉速。它据此判断微信是按全集群的总量限流，于是写了一个调速器，让整队一直贴着上限跑；又在美国开了一台机器做对照，证明换地区也加不上去，8 分钟后就删掉了。具体做法见「爬虫怎么写」。
- **小红书提速：** 在一台机器上逐档上探单个 IP 的速率，到每秒 80 次都没出现挑战页，留出余量定在 70，再分批推到全集群。
- **一万多个小站：** 把这部分约 1,500 万行按网站重新切成任务，给每个站单独调速；跑的过程中，按我的决定放开了几个大图床的上限，放弃了两个大多返回 403 的站。
- **内存：** 发现有机器内存快满，就按计划逐台重启；swap 不够的机器，补了 swap 文件。
- **补下：** 跑完后统计失败的行，只把暂时性的失败单独再下一遍。重下的行里，小红书补回了 98.3%，微信补回了 99.3%。
- **开发机被回收：** 开发机被回收，常驻 agent 跟着停了 1 小时 42 分钟。凭据随后过期，所有机器正常退出。我电脑上的会话临时接管，从另一台开发机推送凭据、重新拉起各条线；开发机回来以后，再交还给常驻 agent。
- **算账：** 按每台机器的开机时长，算出各账户的花费和要补的钱。11 月三个账户合计 94.21 美元，和控制台上的数字一分不差。
- **收尾：** 删掉全部 95 台机器，核对三个账户没有遗留资源，再读完全部约 12 万个完成标记，出全量统计。

这在以前一定是需要一个资深的爬虫工程师来完成的。当然他也会犯错误：

- 用错了全局停止标记，小红书跟着多停了 22 分钟。
- 守护规则「慢 20 分钟就删机重建」到了收尾阶段，会误删正在收尾的机器。后来改成剩下的任务很少时，就关掉这条规则。
- 小站调速一开始把「图大所以慢」和「傍晚线路慢」都当成对方在限流，一度把整队速度砍到三分之一，后来改了判断条件
- 误报，比如报「凭据推送有问题」，或者把正常跑完的线标成要处理。
- 定时巡检有几次没有触发，或者推迟了。

## 摸清对方怎么限流

三类站有三种限法：微信按全集群的总量限，小红书按单个 IP 限，小站各有各的低上限。限法不同，提速的办法也不同。

**怎么看出是总量限流。** 机器从 15 台加到 29 台以后，三个机房的所有机器同时、同比例地掉速，从每台每秒约 600 行掉到 100–150 行，同时出现了平时没有的限流错误码和连接重置。如果是按 IP 限，原来那 15 台不该受影响。我们又在美国另开了一台做对照，结果也一样被限。

**微信：贴着总量上限跑。** 每个进程每 20 秒读一次 S3 上的控制文件，按里面的目标速率均匀地发请求。这样改速率不用重启，新进程也不会一启动就把几百个请求同时打出去。调速器按「加性增、乘性减」来调：连续两轮被限流超过 0.5%，就降到 0.8 倍，并把这个速率记为天花板；平稳 15 分钟，就加每秒 500 次，接近天花板时只加 200。上限会随时间变化：傍晚约每秒 9,000 次，深夜能到 1 万以上。

还有一个细节：卡在我们自己的 CPU 上时，目标要跟着实际速度走（实际值加 500）。否则目标停在高位，CPU 一空出来，速率就会直接冲过去。之前到每秒 10,600 次时，被限流 2–3%；到 14,600 次时，大面积被拒。

**小红书：按单 IP 定速。** 一个 IP 短时间内发到每秒约 400 次，就开始收到 CDN 返回的 JS 挑战页：一段约 1 KB 的 `<script>`，状态码也是 200。我们的规矩是，挑战页就是停的信号：不去解它，不重试那个 URL，也不换 User-Agent 或 IP 去绕。

下载器里有一个熔断器：一个进程最近 500 个应答里有 10 个挑战页，就在 S3 上写一个封锁标记，所有机器的这条线随即停下。每个请求发出前，包括重试，都先查一次这个标记。

定速时，先在一台机器上逐档上探：每秒 64 次连跑 11 分钟没问题，后来试到 80 也没有挑战页，留出余量定在每个 IP 70 次。总速率先和我商量好，再分批加机器，每批 5 台、观察 30–60 分钟，确认小红书不是按总量限。

## 怎么跑快

### 单机

CPU 是瓶颈：每张图下载约花 1 ms、上传约花 0.6 ms 的 CPU，所以一个核跑一个进程。下面是在 Hetzner 上实测的稳定速度：

| 机型 | 配置 | 进程 × 并发 | 每秒行数 | CPU | 内存 |
|---|---|---|---:|---:|---:|
| cpx12 | 1 vCPU、2 GB | 1 × 768 | 335 | 78% | 1.7 GB |
| cpx32 | 4 vCPU、8 GB | 4 × 1024 | 1,354 | 82% | 7.4 GB |

上传也要并行。从欧洲的机房到 S3，单条连接只有约 15 MiB/s，所以把文件切成 8 MiB 的分片多线程上传：8 条连接约 120 MiB/s，32 条约 420 MiB/s。再开 BBR、把 TCP 缓冲区调到 64 MiB，又快了约 10%。

内存方面，每个进程约占 1.5 GB，大多是正在下载的图片。用 `MALLOC_ARENA_MAX=2` 压住 glibc 在多线程下的内存膨胀，2 GB 的小机器再加上 swap。

## 怎么省钱

**流量不额外花钱。** Hetzner 只算出站流量，每台每月含 20 TiB。从 CDN 下载是入站，不算；上传到 S3 是出站，单台最多用了 12.6 TiB，没有超。对 S3 来说这是入站流量，也不收费。所以 744 TB 的流量没有额外花钱。

**按瓶颈选机型。** 受单 IP 限制的线，要的是 IP 多，所以用最便宜的 1 vCPU 机器；受 CPU 限制的线，用独享 vCPU 的机器。

| 机型 | 配置 | 主要用途 | 台数 | 机器·小时 | 花费 |
|---|---|---|---:|---:|---:|
| ccx13 | 2 个独享 vCPU | 微信、知乎 | 19 | 1,106 | $92.3 |
| cpx22 | 2 个共享 vCPU | 微信、知乎 | 19 | 594 | $22.9 |
| cpx12 | 1 个共享 vCPU | 小红书 | 40 | 2,148 | $49.4 |
| cpx32 | 4 个共享 vCPU | 最初的测试、小站 | 17 | 140 | $10.1 |
| 合计 | | | 95 | 3,988 | $174.8 |

**按小时计费，跑完就删。** 一条线跑完，马上排空再删；闲置的机器随手删。一共开过 95 台，峰值同时 66 台，合计 3,988 机器·小时。

**单价。** 算下来每 TB 约 0.23 美元，每百万张约 6 美分。

**总账。** 机器约 175 美元，加上 agent 约 500 美元（按 API 标价折算），合计约 675 美元，大头是 agent。

**和 AWS 粗略对比。** 假设在 AWS 上跑同样的 6,110 vCPU·小时、3,988 个 IP·小时，下载 744 TB，S3 在同一区域，下载入站和写 S3 都免费；两边都要付的 S3 请求费不算。

| 方案 | 机器 | 公网 IPv4 | 流量 | 合计 |
|---|---:|---:|---:|---:|
| Hetzner（实际） | 含 IPv4 | — | 0 | $175 |
| AWS 按需（c7i.large）+ 每台公网 IP | $273 | $20 | 0 | 约 $293 |
| AWS Spot + 每台公网 IP | 约 $86 | $20 | 0 | 约 $106 |
| AWS 按需 + NAT 网关出网 | $273 | — | 约 $33,500 | 约 $33,800 |

和按需实例比，Hetzner 便宜约 40%。Spot 实例按当时的价格反而更便宜，但随时可能被回收，价格也会变。真正的坑是 NAT 网关：它按每 GB 0.045 美元收处理费，744 TB 就要 3 万多美元，是机器费的上百倍，而很多公司集群里的容器默认都走 NAT 出网。

这里把 1 个 Hetzner vCPU 按 1 个 AWS vCPU 算。小红书那条线每个 IP 只要 1 个 vCPU，而 AWS 最小的计算型机器是 2 vCPU，所以 AWS 这几行算低了。NAT 网关和公网 IPv4 的价格来自 AWS 的 VPC 定价页[^aws_vpc_pricing]（每 GB 0.045 美元、每小时 0.005 美元）；c7i.large 按需每小时 0.08925 美元、Spot 约 0.028 美元，来自 Vantage[^vantage_c7i]，2026-11-03 查询；流量按 744,490 GB 算。

## 从国内用 Hetzner：注册、认证和付款

新账户要先过验证，二选一：绑信用卡并预付一笔钱（我们付了 25 美元，直接记成余额），或者上传证件。

申请提额时，客服会问服务器上要跑什么。简单说明是在下载公开数据集的图片，就够了。新账户的共享 vCPU 配额很小，正常要等开户满一个月、付过第一张账单才能提。我们提交工单说明用途后，约两天提到了 100 个共享 vCPU 和 100 个 IP，独享 vCPU 还停在 14 个。

开机两天后，每个账户都收到了身份核实邮件，要求 48 小时内回复并附上护照，否则锁号。有一封进了 Outlook 的垃圾邮件，差点错过。回复后客服解除了限制，机器没有受影响。

付款方面，预付的余额不按天扣，每月发票日一次结清上个月；余额少了也不会停机。信用卡会在出账几天后自动扣款（银联卡除外）。余额不够时怎么和信用卡分摊，文档没写清楚，所以我们在发票日前把余额补够了。余额不能在账户之间转，只有关闭账户、且没有欠账时才退。

| 微信 | 2,189,647,303 | 2,179,565,345 | 99.54% | 446.6 TB | 24.3% |

合计从 2,984,872,339 个 URL 里保存了 2,973,430,108 张（99.62%），共 744.49 TB，其中 38.0% 的图大于 1024²。小红书的图最大，87.6% 大于 1024²；微信和知乎只有四分之一左右。

已知问题：小红书的原图正中都烤进了一个半透明的「小红书」水印，换 CDN 域名也去不掉，只能在下游处理。

## 结论

这次下载最大的体会是，一个常驻的 AI agent，加上写清楚的授权和规则，就能把大部分运维接过去。三天里我只做了约 36 个决定，夜里也不用盯；巡检、调速、事故处理和算账都是它做的。它也会犯错，所以重要的结论要核对，危险操作要先备份，规则要写清例外。

agent 并不便宜。按 API 标价折算约 500 美元，是机器花费的近 3 倍，大头是长会话反复读上下文。

爬虫这边，关键是先弄清每个站怎么限流：总量限流就贴着上限跑；单 IP 限流就按 IP 定速，靠加 IP 提速；小站就各调各的。省钱则靠含流量的机器、按瓶颈选机型和跑完就删。如果换成 AWS 又走 NAT 网关，光流量处理费就要 3 万多美元。
