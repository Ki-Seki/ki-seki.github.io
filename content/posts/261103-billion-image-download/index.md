## 引言

- 任务：把 [OmniCorpus-CW](https://openxlab.org.cn/datasets/Li-Qingyun/OmniCorpus-CW)（公开的中文网页图文交错语料）里 2,984,872,339 个去重后的图片 URL 下成原图，存进 S3，给文生图训练用。
- 数据集只给文字和图片链接，而且大多是缩略图链接（微信 88% 是 `/640`），所以要先改写成原图链接再下。一句话带过，不展开。
- 结果：79 小时 25 分，保存 2,973,430,108 张（99.62%），共 744 TB，机器花费约 175 美元。平均每秒约 1 万张、2.6 GB/s。
- 重点：这三天里几乎所有运维都是 AI agent 做的，我只做要花钱、加资源和有风险的决定。
- 本文讲这套分工怎么搭、agent 实际做了什么、它犯过哪些错，再讲爬虫怎么写、怎么提速和省钱。

## 让 AI agent 来运维

### 分工

- **常驻 agent：** 开发机上的一个 Claude Code，跑在 tmux 里一直不退出。巡检、调速、开删机器、重启、写工作日志和改监控页都由它做。
- **我：** 只批准和决定，比如加机器、提配额、充钱、定截止时间。
- 一个 agent 就够了。我另外在自己电脑上开了一个会话，用来传话和处理要用我账号的事（看邮件、Hetzner 控制台），这只是我这边方便。

### 授权和规则

- 事先给的长期授权：
  - 闲置的机器可以随手删；
  - 运行中不超过 5 台时可以自己开关机；
  - 已经批准的提速可以用任意机型和地区。
- 必须先问我的事：花钱、超过机器上限、停掉整条下载线、碰账号和凭据。
- 硬规则：不删 S3 上的数据，不绕过网站的挑战页。
- 这些规则都写进 agent 的说明文件和记忆里，每次巡检都按它们来。

### agent 实际做了什么

- **节奏：** 白天每小时巡检一次，夜里每 30 分钟一次，另有事件监控实时报警。三天的工作日志写了 2,600 多行。
- **例子**（每个配一两句和数字）：
  - **微信调速：** 加机器后所有机器同时、同比例掉速。它判断出是按全集群总量限流，写了调速器，一直贴着上限跑；又在美国开了一台机器做对照，证明换地区也加不上去，8 分钟后删掉。做法见「爬虫怎么写」。
  - **小红书提速：** 在一台机器上逐档上探单 IP 速率，到 80 都没出现挑战，留余量定在 70，然后分批推到全集群。
  - **一万多个小站：** 把这部分约 1,500 万行按网站重新切任务，给每个站单独调速；跑的过程中按我的决定放开几个大图床的上限，放弃两个大多返回 403 的站。
  - **内存：** 发现内存快满的机器就计划内逐台重启；swap 不够的机器加了 swap 文件。
  - **补下：** 跑完后统计失败的行，单独补下一遍。小红书补回 98.3%，微信补回 99.3%。
  - **开发机被回收：** 常驻 agent 跟着开发机停了 1 小时 42 分，凭据随后过期，所有机器正常退出。我电脑上的会话临时接管，从另一台开发机推凭据、重新拉起各条线；开发机回来后再交回常驻 agent。
  - **算账：** 按每台机器的开机时长算出各账户的花费和要补的钱。11 月三个账户合计 94.21 美元，和控制台一分不差。
  - **收尾：** 删光 95 台机器，核对三个账户没有遗留资源，读完全部 12 万个完成标记出全量统计。

### agent 犯过的错

- 用错了全局停止标记，小红书跟着多停了 22 分钟。
- 一条被我拦下的命令其实已经执行了，首页被换掉；它自己发现后从备份恢复。
- 守护规则「慢 20 分钟就删机重建」到了收尾阶段会误删正在收尾的机器，后来改成剩下的任务很少时就关掉这条规则。
- 小站调速一开始把「图大所以慢」和「傍晚线路慢」都当成对方在限流，一度把整队速度砍到三分之一，后来改了判断条件（见「一万多个小站」）。
- 误报：比如报「凭据推送有问题」，以及把正常跑完的线标成要处理。
- 定时巡检有几次没有触发或者推迟了。
- 对话被压缩后，agent 会凭旧摘要报数，报错过机器台数。
- 教训：
  - 重要结论要有第二个来源核对；
  - 危险操作先备份；
  - 规则里要写清例外情况，比如收尾阶段。

### 好处与代价

- **我花的精力：** 三天里我一共发了约 137 条消息，其中约 36 条是拍板，比如批准、选方案、给授权、定截止时间（不算点按钮的回答）。其余主要是问进度和原理（约 50 条），以及处理账户、充值和邮件（约 30 条）。夜里不用盯。

## 爬虫怎么写

- 要爬的不是成千上万个网站：微信、知乎、小红书三个大 CDN 占了 99.5%，剩下约 1,500 万行散在 1.2 万个小站上。这两类要用不同的写法。

### 一次请求

- **请求头：** 浏览器 User-Agent、`Accept: image/*`、`Accept-Encoding: identity`，不发 Referer。微信看到外站的 Referer 会触发防盗链，返回一张占位图。
- **不请求就跳过：** 动图和矢量图（`wx_fmt=gif`、`wx_fmt=svg`）直接跳过。
- **判断拿到的是不是图：** 非 200、`Content-Type` 是网页或 JSON、微信的 `X-ErrNo` 错误头、小红书的挑战页，都不算。很多站拒绝时不报错，而是返回 200 的网页，所以一定要看内容类型。
- **不解码图片：**
  - 正文长度对上 `Content-Length` 才算下完，短了就重试；
  - 宽高直接从文件头读（JPEG 的 SOF、PNG 的 IHDR、WebP 的 VP8 头等），和完整解码对比 393/393 一致；
  - 之前另一次下载每张都完整解码，CPU 花了很多，截断的文件还是漏了过去。
- **重试分三类：**
  - 429、5xx、超时、连接被重置：带抖动的指数退避，最多 3 次；
  - 限流应答（微信的几种限流错误码、小红书一阵一阵的 424）：等 15、30、60 秒再试；
  - 403、404 这类 4xx：直接记失败，不重试。
- **每个 URL 都记一行索引：** 状态、错误、大小、宽高，下没下成都记。跑完以后只按索引补下暂时性的失败；以后想换尺寸门槛，也不用再下一遍。

### 并发：大 CDN 要长连接和高并发

- 常用的 img2dataset 是为 LAION 这类数据调的：几百万个域名，每个 URL 新开一个连接，超时 2 秒、不重试，成功率 60–70%，开销主要在 DNS 和 TLS 握手上。
- 我们正好相反：只有几个 CDN 主机，从欧洲到深圳的往返很长，几乎每个请求都能成功。所以要复用长连接、放长超时、失败了重试。
- 一开始用线程 + `requests`，一个进程 64 个线程每秒只有约 50 行，客户端自己就是瓶颈。后来改成每个进程一个 asyncio 事件循环、一个 aiohttp 会话，同时有 768–1024 个请求在飞。
- 一张微信原图从欧洲取约 1.2 秒，所以速度约等于并发数除以 1.2，直到 CPU 用满。只下载不上传时，一个进程每秒约 865 行。
- 一个任务在等最慢的几个 URL 时，下一个任务已经开始，长尾不会空占并发。

### 先摸清对方怎么限流

- 三类站三种限法：微信按全集群总量，小红书按单个 IP，小站各有各的低上限。限法不同，提速的办法也不同。
- **怎么看出是总量限流：** 机器从 15 台加到 29 台后，三个机房的所有机器同时、同比例从每台每秒约 600 行掉到 100–150 行，还出现了平时没有的限流错误码和连接重置。在美国另开一台做对照，也一样被限。
- **微信：贴着总量上限跑**
  - 每个进程每 20 秒读一次 S3 上的控制文件，按里面的目标速率均匀地发请求。改速率不用重启，新进程也不会一启动就把几百个请求同时打出去。
  - 调速器加性增、乘性减：连续两轮被限流超过 0.5% 就降到 0.8 倍，并把这个速率记为天花板；平稳 15 分钟就加 500 次/秒，接近天花板时只加 200。
  - 上限随时间变：傍晚约每秒 9,000 次，深夜能到 1 万以上。
  - 卡在自己的 CPU 上时，目标改成跟着实际速度走（实际值加 500）。否则目标停在高位，CPU 一空出来就会直接冲过去：之前到 10,600 时被限流 2–3%，到 14,600 时大面积被拒。
- **小红书：按单 IP 定速**
  - 一个 IP 短时间内发到约每秒 400 次，就开始收到 CDN 返回的 JS 挑战页（约 1 KB 的 `<script>`，状态码也是 200）。
  - 规矩：挑战页就是停的信号。不解、不重试那个 URL，也不换 User-Agent 或 IP 去绕。
  - 熔断：一个进程最近 500 个应答里有 10 个挑战，就在 S3 上写一个封锁标记，所有机器的这条线随即停下；每个请求发出前（包括重试）都先查一次。
  - 先在一台机器上逐档上探：每秒 64 次连跑 11 分钟没问题，后来试到 80 也没有挑战，留余量定在每 IP 70。
  - 总速率先和我定好，再分批加机器，每批 5 台看 30–60 分钟，确认它不是按总量限。

### 一万多个小站

- 剩下约 1,500 万行来自约 1.2 万个域名：百度百科约 1,040 万，新浪、36 氪、中新网各约 100 万，其余是长尾，不少是 gov.cn 和报社电子版。
- **按网站切任务：** 原来的任务按哈希分桶切，一个任务里混着几百个网站，同一个小站会被很多进程同时请求，没法按站限速。所以先把这些行抽出来，按网站排序重新切，让一个小站只出现在一个任务里。这样一个进程里的速率，就是全集群对这个站的速率。网站按注册域名算，`img.x.gov.cn` 和 `www.x.gov.cn` 共用一份额度。
- **每个站自己调速：**
  - 普通小站从每秒 0.5 次起步、最多 2 次、同时 2 个连接；gov.cn 和电子报从 0.3 起步、最多 1 次、1 个连接；大图床单独给上限。
  - 每 60 秒看一次：没有错误、而且请求确实在排队，就乘 1.5；错误（403、429、5xx、连不上）超过 10% 就减半，并保持 5 分钟。
  - 超时：连接 10 秒、读取 30 秒，一个请求最多 90 秒，免得一个挂住的小站拖住整个任务。
- **两个坑：**
  - 「慢」要按每 100 KB 算：36 氪和中新网的原图大，一张要多花三倍时间，按每次请求算，它们就一直被当成慢站压在最低速。
  - 只慢不报错不算限流：傍晚中欧线路本身就会慢三倍，只因为慢就给每个站减半，一度把整队速度砍到三分之一。后来改成慢的同时还有错误才减速。
- **死站和拒绝：** 连续 10 次连不上，就当这个站挂了，15 分钟内不再请求；最近 50 个应答里有 45 个是 401/403/451 或网页，就不再请求它（新京报的图全部返回网页）。
- **百度百科要不要 Referer：** 抽 50 个地址，带和不带各请求一次，结果完全一样，所以不带。
- **结果：** 1,501 万行保存了 1,412 万张（94%）。没下到的主要是站挂了或连不上（约 27 万）、被拒（约 25 万）、按设计跳过的 GIF/SVG（约 13 万）和死链（约 11 万）。

## 怎么跑快

### 单机

- **CPU 是瓶颈：** 每张图下载约 1 ms、上传约 0.6 ms，所以一个核跑一个进程。
- 表：实测，1 核的 cpx12 约 335 行/秒，4 核的 cpx32 约 1,354 行/秒。
- **上传：** 跨洲单条连接只有约 15 MiB/s，改成 8 MiB 分片多线程上传：8 条约 120 MiB/s，32 条约 420 MiB/s。BBR 加上 64 MiB 的 TCP 缓冲区又快了约 10%。
- **内存：** 每个进程约 1.5 GB，用 `MALLOC_ARENA_MAX=2` 压住 glibc 的内存膨胀，2 GB 的小机器加 swap。

### 长尾

- 最后几十个任务拖着整队机器，于是定一个截止时间。到点时没下到的行标成「截止未下」，已经下好的照常写完成标记。

## 怎么省钱

- **流量：** Hetzner 每台每月含 20 TiB 流量，单台最多用了 12.6 TiB；数据写进 S3 是入站流量，不收费。所以 744 TB 的流量没有额外花钱。
- **按瓶颈选机型：**
  - 受单 IP 限制的线，用最便宜的 1 vCPU 机器，因为每个 IP 越便宜越好；
  - 受 CPU 限制的线，用独享 vCPU 的机器。
- 表：机型、台数、机器·小时、花费（ccx13、cpx12、cpx22、cpx32）。
- **按小时计费：** 一条线跑完马上排空再删，闲置的随手删。一共开过 95 台，峰值同时 66 台，合计 3,988 机器·小时。
- **单价：** 约每 TB 0.23 美元，每百万张约 6 美分。
- **总账：** 机器约 175 美元，加上 agent 约 500 美元（API 标价折算），合计约 675 美元，大头是 agent。
- **和 AWS 粗略对比：** 同样 6,110 vCPU·小时、3,988 个 IP·小时、744 TB 下载量。假设 S3 在同一区域，下载入站和写 S3 都免费；两边都要付的 S3 请求费不算。

| 方案 | 机器 | 公网 IPv4 | 流量 | 合计 |
|---|---:|---:|---:|---:|
| Hetzner（实际） | 含 IPv4 | — | 0 | $175 |
| AWS 按需（c7i.large）+ 每台公网 IP | $273 | $20 | 0 | 约 $293 |
| AWS Spot + 每台公网 IP | 约 $86 | $20 | 0 | 约 $106 |
| AWS 按需 + NAT 网关出网 | $273 | — | 约 $33,500 | 约 $33,800 |

- 结论：
  - 和按需比，Hetzner 便宜约 40%。Spot 按当时的价格反而更便宜，但随时会被回收，价格也会变。
  - 真正的坑是 NAT 网关：每 GB 收 0.045 美元处理费，744 TB 要 3 万多美元，是机器费的上百倍。很多公司集群里的容器默认都走 NAT 出网。
  - 1 个 Hetzner vCPU 按 1 个 AWS vCPU 算。小红书那条线每个 IP 只要 1 个 vCPU，而 AWS 最小的计算型机器是 2 vCPU，所以 AWS 这几行偏低。
- 价格来源：AWS VPC 定价页（NAT 每 GB $0.045，公网 IPv4 每小时 $0.005）；c7i.large 按需每小时 $0.08925、Spot 约 $0.028（Vantage，2026-11-03 查）；流量按 744,490 GB 算。

## 从国内用 Hetzner：注册、认证和付款

- **注册和验证：** 新账户要先过验证，二选一：绑信用卡并预付一笔（我们付了 25 美元，直接记成余额），或者上传证件。
- **用途说明：** 申请提额时，客服会问「服务器上要跑什么」。简短说明是在下载公开数据集的图片，就够了。
- **配额：** 新账户的共享 vCPU 配额很小，正常要等开户满一个月、付过第一张账单才能提。我们提交工单说明用途后，约两天提到了 100 个共享 vCPU 和 100 个 IP；独享 vCPU 还停在 14。
- **身份核实：** 开机两天后，每个账户都收到身份核实邮件，要求 48 小时内回复并附上护照，否则锁号。
  - 有一封进了 Outlook 的垃圾邮件，差点错过。
  - 回复后客服移除了限制，机器没受影响。
- **付款：**
  - 预付余额不按天扣，每月发票日一次结清上个月；余额少了也不会停机。
